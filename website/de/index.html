Selbst gehostete Dokumentation

Deine Dokumentation liegt in Git, nicht in einer Datenbank.

DocuWaves ist eine Dokumentationsseite, die du selbst betreibst. Jedes Projekt, jede Kategorie und jede Seite ist eine Markdown-Datei in einem Git-Repository, das dir gehört – und jedes Speichern im Browser-Editor ist ein Commit. Verlauf, Diffs, Autorenschaft und Wiederherstellen sind keine Funktionen obendrauf; sie sind einfach das Repository.

Zur Dokumentation Quellcode auf GitHub
Auf einem Linux-Server installieren 
curl -fsSL https://get.docuwaves.app | sudo sh

Fragt nach einer Domain, richtet DocuWaves hinter Caddy mit einem Let's-Encrypt-Zertifikat ein, legt nächtliche Backups und den Befehl docuwaves an und zeigt einen einmaligen Einrichtungscode für das erste Konto. Debian, Ubuntu, Rocky und Alma; amd64 und arm64. Erst das Skript lesen oder selbst mit Docker Compose starten.

Inhalte in Git

Jedes Speichern ist ein lesbarer Commit

DocuWaves führt keine eigene Versionstabelle. Der Verlauf einer Seite ist der Git-Verlauf ihrer Datei – die App und git log geben also dieselbe Antwort.

  • Verlauf, Diffs und Wiederherstellen inklusive Jede Seite hat einen Verlauf-Tab: Commits mit Autor, Datum und Nachricht, ein farbiger Diff pro Änderung und ein Wiederherstellen, das den alten Text als neuen Commit obendrauf schreibt – nichts wird umgeschrieben oder gelöscht.
  • Die Datenbank ist nur ein Index Standardmäßig SQLite, auf Wunsch PostgreSQL. In beiden Fällen enthält sie keine eigenen Inhalte, nur einen Such- und Navigationsindex über die Dateien. Löschst du sie, baut DocuWaves sie beim nächsten Start aus dem Repository neu auf.
  • Die Dateien überleben die App Markdown mit einem kurzen YAML-Kopf, in einer lesbaren Ordnerstruktur. Jemand kann das Inhalts-Repository forken, eine .md-Datei ändern und einen Pull Request stellen; DocuWaves übernimmt die gemergte Änderung von selbst.

KI-Assistenten

Gib einem Assistenten Schreibrechte – und behalte den Überblick

DocuWaves spricht MCP. Richte einen Assistenten mit einem Bearer-Token auf /api/mcp, und er kann deine Dokumentation durchsuchen, lesen und – wenn das Token es erlaubt – schreiben. Jede Änderung kommt als gewöhnlicher Commit an, mit dem Token als Autor.

Die üblichen Werkzeuge beantworten also Fragen dazu:

git log --author='API token' # alles, was Assistenten schrieben git log --author='notes-bot' # nur dieses eine Token git revert <sha> # eine Änderung zurücknehmen
  • Ein Lösch-Werkzeug gibt es bewusst nicht Ein Assistent kann Seiten anlegen und umschreiben, und beides lässt sich zurückholen – eine falsche Änderung ist sichtbar und ein git revert entfernt. Löschen ist die Operation, deren Schaden man hinterher nicht sieht, deshalb bleibt sie in der Verwaltung, wo ein Mensch sie bestätigt.
  • Lesen und Schreiben sind getrennt Lesen ist im Formular voreingestellt. Ruft ein Lese-Token ein Schreib-Werkzeug auf, wird das abgelehnt, mit der Berechtigung, die es hat, und der, die es bräuchte. Tokens können ablaufen, und ein Widerruf gilt ab der nächsten Anfrage.
  • Das Token öffnet genau eine Tür Ein API-Token gilt für /api/mcp und sonst nichts – es erreicht weder die übrige Verwaltungs-API noch das Branding und kann kein weiteres Token anlegen. Umgekehrt akzeptiert der Endpunkt keine Admin-Sitzung aus dem Browser.
  • Es kostet keine KI-Gebühren Der Endpunkt ist ein Werkzeug-Server. Er beantwortet die Anfragen eines Assistenten zu deiner Dokumentation und ruft selbst nie ein Sprachmodell auf.

Zusammenarbeit

Mehrere Leute, ohne Rechte-Labyrinth

Vier Rollen, eine optionale Freigabe und eine Möglichkeit, einen Entwurf jemandem ohne Konto zu zeigen. Jedes davon ist eine kleine, klare Regel statt einer Matrix zum Konfigurieren.

  • Konten mit vier Rollen Leser für private Projekte, Lesen für Prüfende, die Entwürfe und Verlauf sehen, aber nichts ändern, Schreiben für die Dokumentation, Verwalten für die Instanz selbst. Passwort oder Single Sign-on per OIDC, dazu Zwei-Faktor-Anmeldung mit Sicherheitsschlüssel wie YubiKey, Passkey oder Authenticator-App.
  • Freigabe vor dem Veröffentlichen, pro Projekt Eine Einstellung im Projekt, und nichts darin geht online, bevor eine zweite Person zustimmt. Ohne sie arbeitet ein Projekt genau wie vorher.
  • Vorschau-Links für Entwürfe Schicke eine unveröffentlichte Seite an jemanden ohne Konto, über einen Link, der abläuft und sich zurückziehen lässt.
  • Private Projekte Ein Projekt, das nur angemeldete Lesende öffnen können, neben öffentlichen in derselben Instanz.
  • Wer bearbeitet gerade mit Der Editor zeigt, wer die Seite noch offen hat. Ein Speichern, das eine neuere Fassung von jemand anderem überschreiben würde, wird angehalten und gezeigt, nicht still zusammengeführt.
  • Webhooks an Discord, Slack, Teams, Matrix oder jede URL Kündige veröffentlichte Seiten und Seiten, die auf Freigabe warten, dort an, wo das Team ohnehin liest.

Bestehende Doku übernehmen

Fang mit dem an, was du schon hast

Der Umzug zu DocuWaves ist ein Import, kein Neuschreiben. Und Dokumentation, die schon neben dem Code liegt, kann dort bleiben.

  • Ein ZIP mit Markdown Exporte aus MkDocs, GitBook, Docusaurus und Obsidian werden erkannt, oder einfach ein Ordner mit .md-Dateien. Eine Vorschau zeigt, was passieren würde, bevor etwas geschrieben wird; Links werden umgeschrieben und Bilder kopiert.
  • Confluence und Notion Ein HTML-Bereichsexport aus Confluence oder ein „Markdown & CSV“-Export aus Notion wird zu einem Projekt mit Kategorien, Seiten und Bildern.
  • Docs-as-Code aus deiner CI Behalte einen Ordner docs/ im Code-Repository und lass einen CI-Schritt ihn bei jedem Push schicken. Ein Release-Tag friert ihn als Version ein. Die Dokumentation von DocuWaves selbst wird genau so veröffentlicht.

Loslegen

Kein Konto, und auch kein Git-Hoster

Es gibt keinen Schritt, in dem du erst ein Repository anlegst, ein Token erzeugst oder dich irgendwo registrierst. Beim ersten Start führt DocuWaves git init in seinem eigenen Datenvolume aus, und jede Seite, die du danach schreibst, ist dort ein echter Commit.

  • Lokal ist eine vollständige Einrichtung, keine Testversion Vollständiger Seitenverlauf, Diffs, Wiederherstellen, Autorenschaft und Inhalte als einfaches Markdown, das du auch außerhalb der App lesen kannst. Das Einzige, was fehlt, ist eine Kopie an einem anderen Ort.
  • Ein Remote lässt sich jederzeit ergänzen Trag die URL eines leeren Repositorys in die .env ein und starte neu. Der vorhandene Verlauf wird vollständig hochgeladen – jeder Commit, nicht zu einem Import zusammengefasst – und ab dann verhält sich die Instanz, als wäre sie vom ersten Tag an mit Remote eingerichtet. Entfernst du die URL wieder, ist sie lokal, mit allem Verlauf.
  • Also: das Volume sichern Bei einer rein lokalen Instanz ist ./data die einzige Kopie deiner Dokumentation, und nichts spiegelt sie. Sichere diesen Ordner, klone ihn woandershin oder ergänze ein Remote – wie bei allen anderen Daten, die dir fehlen würden.

Der Alltag

Der Rest, kurz gefasst

  • Visuell oder in Markdown schreibenSchreib visuell mit einer Werkzeugleiste oder in Markdown mit Live-Vorschau. Die Datei ist in beiden Fällen Markdown, und beim Wechseln geht nichts verloren.
  • Hinweisboxen, Tabs und SnippetsFarbige Hinweise, Tab-Gruppen, wiederverwendbare Snippets und {{variables}}, alles als einfacher Text, der auch auf GitHub gut lesbar bleibt.
  • Diagramme als TextEin mermaid-Block wird als echtes Diagramm gezeichnet – in der Vorschau, auf der veröffentlichten Seite und in GitHubs eigener Dateiansicht.
  • Bilder per Einfügen oder ZiehenFüg einen Screenshot in den Editor ein oder zieh Dateien darauf: hochgeladen nach assets/ im Projekt, committet und an der Cursorposition eingefügt.
  • Ungespeichertes bleibt erhaltenText im Editor wird im Browser aufbewahrt und beim Zurückkommen angeboten – nie still übernommen und nie hochgeladen.
  • VolltextsucheÜber alle veröffentlichten Seiten aller Projekte, in der Sprache und Version, die gerade gelesen wird, und tolerant bei Tippfehlern. Wonach gesucht und nichts gefunden wurde, wird dir aufgelistet.
  • PDF und DruckEin ganzes Projekt oder ein Kapitel als druckbares Handbuch mit Titelseite und Inhaltsverzeichnis, und jede einzelne Seite druckt sauber.
  • Änderungsprotokoll und RSSEine Seite „Was ist neu?“ und Feeds, gebaut aus dem Verlauf des Repositorys, damit Lesende Änderungen verfolgen können.
  • Die Doku fragen, optionalEin Fragefeld, das nur aus deinen veröffentlichten Seiten antwortet, mit Quellen. Standardmäßig aus; funktioniert auch mit einem lokalen Modell wie Ollama.
  • Mehrere Projekte, eine InstanzEine Installation dient der Doku für jedes Werkzeug, das du pflegst, jeweils mit eigenen Kategorien und Seiten, als Kacheln dargestellt.
  • Mehrere Sprachen, optionalEine Seite kann es in mehreren Sprachen unter einem Slug geben, mit der Sprache in der URL und einem ehrlichen Hinweis auf noch nicht übersetzten Seiten.
  • Eingefrorene Versionen, optionalFriere die Doku zu einem Release ein, und sie bleibt so: schreibgeschützt und lesbar, während du an der aktuellen weiterarbeitest.
  • EntwürfeEine Seite bleibt für Lesende unsichtbar, bis du sie veröffentlichst, und ein Projekt ohne veröffentlichte Seiten bleibt ganz von der öffentlichen Seite fern.
  • Branding pro InstanzName, Logo, Favicon, Akzentfarbe und Fußzeile kommen aus einer _site.yml im Inhalts-Repository – versioniert und prüfbar wie eine Seite.
  • Passwort oder OIDC-SSOAnmeldung mit Passwort oder über jeden gängigen OIDC-Anbieter – Authentik, Keycloak, Authelia, Zitadel.
  • Backups und DiagnoseEin vollständiger Export mit einem Klick, nächtliche Backups mit dem Installer und eine Diagnoseseite, die sagt, was eingerichtet ist und was nicht.
  • Echtes HTML für CrawlerJede öffentliche URL kommt mit eigenem Titel, Beschreibung, Open-Graph-Tags, Canonical und strukturierten Daten, dazu /sitemap.xml und /robots.txt.

In etwa einer Minute ausprobiert

Docker mit dem Compose-Plugin ist die einzige Voraussetzung. Nichts muss vorher angelegt, registriert oder eingerichtet werden.

Mit Docker Compose installieren
git clone https://github.com/Syntaxlab-dev/DocuWaves.git
cd DocuWaves
cp .env.example .env
docker compose up -d --build
# dann http://<dein-server>:8091 öffnen

Jede Einstellung in der .env hat einen funktionierenden Standardwert. Lieber nichts bauen? Nimm das fertige Image ghcr.io/syntaxlab-dev/docuwaves:stable.
